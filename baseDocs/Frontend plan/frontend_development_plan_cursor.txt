UPDATED FRONTEND DEVELOPMENT PLAN
Next.js Storefront + Admin Dashboard + Express JWT API Integration
Prepared for: Kedame Gebeya E-commerce Platform
Frontend: Next.js + TypeScript + Tailwind CSS + shadcn/ui
Backend: Express.js + JWT + Supabase PostgreSQL, Storage, and Realtime

============================================================
1. FRONTEND STRATEGY SUMMARY
============================================================

This document defines the implementation plan for the complete frontend application.
It is intended to be placed in the root of the frontend project and used by Cursor Agent as the primary development execution guide together with:
- The Frontend SRD / Frontend Development Task Document.
- The backend Postman collection.
- Any approved design reference or starter template.

The SRD remains the main source of truth. This document must not replace or rewrite the SRD. It converts the SRD into a staged frontend implementation sequence.

Core architecture:
Next.js Frontend -> Express API -> Supabase PostgreSQL / Supabase Storage / Supabase Realtime

Important frontend rules:
- The frontend must never connect directly to Supabase PostgreSQL.
- The frontend must never upload directly to Supabase Storage.
- The Supabase service role key must never exist in the frontend project.
- All protected application requests must go through the Express API.
- Authentication is owned by Express using JWT access and refresh tokens.
- Supported login methods are phone OTP and Google OAuth only.
- No password login interface must be created.
- Public product availability text must not be displayed.
- Only visible, non-deleted products returned by the API may be rendered publicly.
- Guest cart data must be stored locally and merged into the server cart after login.
- Payment method is Cash on Delivery only.
- Customer order cancellation must obey the backend cancellation setting.
- Customer order status changes are shown through in-app notifications, not customer SMS.
- Admin product deletion is a soft-delete operation controlled by the backend.
- The UI must work on mobile, tablet, and desktop.
- The application must support light mode and dark mode.
- The implementation must be accessible, keyboard-friendly, and production-ready.

6. API CLIENT AND AUTHENTICATION STRATEGY
============================================================

6.1 API client

Create a single API client responsible for:
- Base URL configuration.
- JSON serialization.
- FormData uploads.
- Authorization headers.
- API error normalization.
- Access token refresh.
- Request retry after refresh.
- Logout when refresh fails.
- Avoiding infinite refresh loops.

The API client must support:
- Public requests.
- Authenticated customer requests.
- Admin requests.
- Multipart product image requests.
- Query parameters.
- Abort signals when appropriate.

6.2 Token handling

Preferred security approach:
- Refresh token in a secure httpOnly cookie controlled by Express.
- Access token held in memory and refreshed when required.

Fallback if the backend currently returns both tokens in JSON:
- Store the access token in memory where practical.
- Persist only what is necessary for page reload recovery.
- Do not use insecure token handling without documenting the risk.
- Never put refresh tokens in URLs.

The implementation must match the backend's actual behavior from the Postman collection.

6.3 Session bootstrap

On application startup:
1. Attempt to restore the existing session.
2. Call GET /api/auth/me when an access token is available.
3. If access token is expired, call POST /api/auth/refresh once.
4. Retry /api/auth/me.
5. Store the returned user in auth state.
6. Merge guest cart after successful customer login.
7. Redirect admin users to the correct admin experience only when requested; do not force redirect from every public page.

6.4 Route protection

Customer protected routes:
- /account
- /account/profile
- /account/addresses
- /account/orders
- /account/orders/:id
- /account/notifications
- /checkout

Admin protected routes:
- /admin
- /admin/products
- /admin/categories
- /admin/orders
- /admin/customers
- /admin/settings
- /admin/sms

Protection rules:
- Unauthenticated users are redirected to login with a return URL.
- Authenticated customers cannot access admin routes.
- Admin UI is not considered a security boundary; the backend must still enforce role authorization.
- Loading state must be shown while session restoration is in progress.

============================================================
7. UX AND DESIGN SYSTEM RULES
============================================================

Visual direction:
- Clean, sharp, modern e-commerce interface.
- Light theme is the primary presentation.
- Dark mode must be fully supported.
- Strong spacing, restrained color usage, readable typography, and clear product imagery.
- Avoid excessive gradients, glass effects, oversized shadows, and clutter.

Responsive behavior:
- Mobile-first implementation.
- Product grids adapt from one column to multiple columns.
- Navigation becomes compact on mobile.
- Admin tables must remain usable through horizontal scrolling or card conversion.
- Forms must not overflow on small screens.
- Buttons must have touch-friendly sizes.

Accessibility:
- Semantic headings.
- Labels for all inputs.
- Visible focus states.
- Keyboard-operable menus and dialogs.
- Sufficient color contrast in both themes.
- Alternative text for meaningful images.
- aria-live or equivalent feedback for async form submissions where appropriate.
- Do not communicate status using color alone.

Loading and errors:
- Use route loading files for major routes.
- Use component skeletons for lists and cards.
- Use actionable errors instead of raw server messages.
- Preserve form data when a recoverable request fails.
- Distinguish empty state from loading and error states.

============================================================
8. DOMAIN RULES TO ENFORCE IN THE UI
============================================================

Products:
- Never render public availability text.
- Hidden and deleted products should not appear in public views.
- Admin can manage visibility.
- Admin image manager supports a maximum of three images.
- Cover image and image order must be manageable.

Cart:
- Guest cart is local.
- Authenticated cart is server-based.
- Guest cart merges after login.
- Product IDs, quantity, volume, and measurement unit must match API expectations.
- Current backend product pricing is authoritative at checkout.

Orders:
- Cash on Delivery is the only payment option.
- Order starts as Pending.
- Customer sees only own orders.
- Admin can update order status.
- Customer cancellation button is shown only when the backend says cancellation is allowed and the order is eligible.
- Do not claim cancellation succeeded until API confirmation.

Notifications:
- Status changes create in-app notifications.
- Unread count must update after read actions.
- Realtime is optional until safely configured.
- Polling or query invalidation may be used as an interim fallback.

Admin:
- Admin can manage categories, products, images, orders, customers, settings, and SMS tests/logs.
- Destructive actions require confirmation.
- Soft-delete wording should use user-friendly labels such as Archive/Delete while explaining recoverability where relevant.
- Restore actions must be supported for categories and products when provided by the API.
