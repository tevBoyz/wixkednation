Software Requirements Document
E-Commerce Web Application with Admin Panel, Age Gate, COD Orders, Supabase Backend Services
1. Project Overview
1.1 Project Name
E-Commerce Product Ordering Web Application
1.2 Purpose
The purpose of this project is to develop a mobile-first e-commerce web application where users can browse products, add products to cart as guests, authenticate only when checking out, place Cash on Delivery orders, and track their order status through their user profile.
The system will also include an admin dashboard where administrators can manage products, categories, orders, customer details, image uploads, SMS settings, and customer cancellation settings.
The application will enforce an age-gate before users can access the public website.
2. Technology Stack
2.1 Frontend
Next.js will be used for the frontend.
Reasons:
SEO-friendly public pages
Good routing structure
Works well for landing pages, product pages, cart, checkout, profile, and admin panel
Supports server-side rendering and static generation where needed
Good developer ecosystem
2.2 Backend
Express.js will be used as the main backend API layer.
The frontend will not directly perform sensitive Supabase operations. Instead, the frontend will call the Express API, and Express will communicate with Supabase.
Architecture:
Next.js Frontend → Express.js API → Supabase
2.3 Database
Supabase PostgreSQL will be used as the main database.
2.4 Authentication
Supabase Auth will be used through the Express API relay.
Supported authentication methods:
Phone number + OTP
Google OAuth
No email/password authentication is required.
2.5 File Storage
Supabase Storage will be used for product image uploads.
Product image uploads, replacements, deletions, and bucket cleanup will be controlled through the Express API.
2.6 Realtime Notifications
Supabase Realtime will be used for customer order status notifications.
When an admin updates an order status, the backend will create a notification record in Supabase, and the customer frontend will receive the update in real time.
2.7 Codebase
JavaScript may be used for the codebase.
TypeScript is recommended if the project is expected to grow, because the system includes roles, orders, status rules, image limits, authentication flows, and admin permissions.

4. Core Business Rules
4.1 Age Gate Rule
All users must pass an age verification gate before accessing the website.
The age gate must ask:
Are you over 21?
If the user selects “Yes,” access is allowed for the current session.
If the user selects “No,” the user must be shown a hard block page.
The user should not be able to bypass the block by refreshing, using back navigation, or directly accessing public URLs during the blocked session.
4.2 Product Visibility Rule
Product visibility is controlled only by the admin.
Public users must not see “Available” or “Not Available” text.
If a product is hidden or unavailable, it should simply not appear on the public website.
Public product listing must only show products where:
isVisible = truedeletedAt = null
4.3 Guest Cart Rule
Guests can fully use the cart without logging in.
Guest cart data must be stored in browser localStorage or sessionStorage.
When a guest clicks checkout:
Cart data is saved locally.
User is redirected to login.
After successful login, the cart is restored.
The frontend sends the guest cart to the backend.
Backend validates the products and prices.
Guest cart is merged with the customer’s server-side cart.
4.4 Checkout Rule
Checkout requires login.
The system does not use online payment.
All orders are Cash on Delivery.
When an order is placed:
Order status = PendingPayment method = COD
The customer sees an order confirmation page.
Admin phone numbers receive SMS alerts for the new order.
Customers do not receive SMS for order status updates.
4.5 Order Status Rule
Supported order statuses:
PendingConfirmedOut for DeliveryDeliveredCancelled
Admin can update order status.
Customers can only see their own order status.
Customers receive real-time in-app/site notifications when order status changes.
4.6 SMS Rule
SMS is used only for:
Customer login OTP
Admin alerts when a new order is placed
SMS must not be sent to customers for order status updates.
4.7 Soft Delete Rule
All deletions must be soft deletes.
Records should not be permanently removed from the database during normal admin operations.
Soft deleted records should use:
deletedAt
A record is considered active only when:
deletedAt = null
4.8 Customer Cancellation Rule
Customer cancellation must be controlled by an admin setting.
If cancellation is enabled:
Customer can cancel eligible orders from profile.
Usually only Pending orders should be cancellable by the customer.
If cancellation is disabled:
Cancellation button must be hidden from customer UI.
Backend must reject customer cancellation requests.

15. Acceptance Criteria
The project is accepted when:
Users cannot access the site without passing the age gate.
Users who answer “No” are blocked.
Guests can browse products.
Guests can add items to cart.
Guests are redirected to login only when checking out.
Guest cart is restored after login.
Customers can place Cash on Delivery orders.
Admin receives SMS alerts for new orders.
Customers do not receive SMS for order status updates.
Customers can view order history.
Customers receive real-time in-app/site notifications.
Admin can create, edit, hide, show, and soft delete products.
Hidden products do not appear publicly.
Admin can upload up to 3 product images.
Old replaced images are deleted from storage.
Admin can create and manage categories.
Admin can update order status.
Customer cancellation works only when enabled by admin.
Supabase service role key is never exposed to frontend.
All protected APIs enforce authentication and role permissions.
