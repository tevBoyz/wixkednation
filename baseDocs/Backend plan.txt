UPDATED BACKEND DEVELOPMENT PLAN
Express.js API + JWT Auth + Supabase PostgreSQL, Storage, and Realtime
Default SMS Provider: AfroMessage
Prepared for: Next.js frontend + Express backend + Supabase infrastructure

============================================================
1. STRATEGY CHANGE SUMMARY
============================================================

The authentication strategy is changed from Supabase Auth to Express-owned JWT authentication.

Old auth strategy:
- Supabase Auth handled phone OTP and Google OAuth.
- Express verified Supabase access tokens.
- users table linked to Supabase Auth user IDs.

New auth strategy:
- Express owns all authentication.
- Express generates and verifies JWT access tokens.
- Express handles phone OTP generation and verification.
- Express sends OTP SMS through AfroMessage by default.
- Express handles Google OAuth start and callback.
- Supabase is used only for:
  - PostgreSQL database hosting
  - Supabase Storage bucket
  - Supabase Realtime for notification subscriptions
- Supabase Auth is not used.

Core architecture:
Next.js Frontend -> Express API -> Supabase PostgreSQL / Supabase Storage / Supabase Realtime

Important backend rules:
- Frontend must never write directly to Supabase database.
- Frontend must never write directly to Supabase Storage.
- Supabase service role key must never be exposed to frontend.
- All authentication must go through Express.
- Express issues JWT access tokens and refresh tokens.
- Phone OTP and Google OAuth are the only login methods.
- No password login.
- SMS provider must be abstracted so AfroMessage can later be replaced with Twilio, Vonage, MessageBird, or another international provider.
- Payment method remains Cash on Delivery only.
- All deletes remain soft deletes.
- Public product availability text should not be shown.
- Admin controls product visibility.
- Guest cart remains in frontend localStorage/sessionStorage and is merged after login.
- Customer cancellation is allowed until Delivered (Pending, Confirmed, OutForDelivery) with cancelledFromStatus acknowledgement; no admin toggle.
- Admin-only reputation tracks successful deliveries and customer cancels.
- Admin new-order alerts use SMS.
- Customer order status updates do not send SMS.
- Order status updates create customer notifications.

- Frontend subscribes to notifications table changes for the logged-in customer if RLS/realtime policy is configured safely

SMS:
- Default provider: AfroMessage
- SMS provider interface must support replacement later
- Uses:
  - Customer OTP
  - Admin new-order alerts
  - Admin test SMS
- Does not send customer SMS for order status changes

Authentication:
- Express-generated JWT access token
- Express-generated refresh token
- Refresh token stored hashed in database
- Optional secure httpOnly cookie for refresh token
- Access token returned to frontend and used as Bearer token
- Refresh endpoint rotates refresh tokens

Google OAuth:
- Express handles Google OAuth start and callback
- Google OAuth verifies Google profile
- Express creates or updates local user
- Express issues JWT access token and refresh token

6. AUTHENTICATION FLOW
============================================================

6.1 Phone OTP send

Endpoint:
POST /api/auth/otp/send

Request:
{
  "phone": "+251911000000"
}

Backend logic:
1. Normalize phone number.
2. Validate E.164 Ethiopian format initially.
3. Apply rate limiting.
4. Generate 6-digit OTP.
5. Hash OTP.
6. Save OTP challenge with expiry.
7. Send SMS using SMS service abstraction.
8. Default provider implementation: AfroMessage.
9. Log SMS result.
10. Return generic success response.

Response:
{
  "success": true,
  "message": "OTP sent successfully if the number is valid."
}

Security:
- Do not reveal whether phone is registered.
- Do not return OTP in response.
- Do not log OTP in plain text.
- Rate limit by phone and IP.

6.2 Phone OTP verify

Endpoint:
POST /api/auth/otp/verify

Request:
{
  "phone": "+251911000000",
  "token": "123456"
}

Backend logic:
1. Normalize phone.
2. Find latest active OTP challenge.
3. Confirm not expired.
4. Confirm not consumed.
5. Confirm attempts < maxAttempts.
6. Compare hashed OTP.
7. If invalid, increment attempts.
8. If valid, mark challenge consumed.
9. Find user by phone.
10. If user does not exist, create customer user.
11. Create or update auth_accounts row for phone provider.
12. Set isPhoneVerified=true.
13. Issue JWT access token.
14. Issue refresh token.
15. Store hashed refresh token.
16. Return user and tokens.

Response:
{
  "success": true,
  "message": "OTP verified successfully.",
  "user": {
    "id": "...",
    "name": null,
    "phone": "+251911000000",
    "email": null,
    "role": "customer"
  },
  "tokens": {
    "accessToken": "...",
    "refreshToken": "..."
  }
}

6.3 Google OAuth start

Endpoint:
GET /api/auth/google/start

Backend logic:
1. Generate Google OAuth authorization URL.
2. Include secure state parameter.
3. Redirect user to Google.

6.4 Google OAuth callback

Endpoint:
GET /api/auth/google/callback

Backend logic:
1. Validate OAuth state.
2. Exchange code for Google tokens.
3. Verify Google ID token.
4. Extract Google subject ID, email, and name.
5. Find auth_accounts row by provider=google and providerAccountId.
6. If found, load user.
7. If not found, find user by email.
8. If still not found, create customer user.
9. Create/update auth_accounts row.
10. Set isEmailVerified based on Google claim.
11. Issue JWT access token and refresh token.
12. Redirect to frontend with short-lived auth handoff code or tokens.

Recommended secure redirect:
- Do not put long-lived refresh token in URL.
- Better option: create one-time auth_handoff_code table.
- Redirect to frontend with ?code=...
- Frontend exchanges code through POST /api/auth/exchange-code.
- For MVP, token in URL may work but is less secure.

6.5 Auth me

Endpoint:
GET /api/auth/me

Auth:
Customer/Admin

Backend logic:
1. Verify Bearer JWT access token.
2. Load user from database.
3. Reject deleted user.
4. Return current user.

6.6 Refresh token

Endpoint:
POST /api/auth/refresh

Request:
{
  "refreshToken": "..."
}

Backend logic:
1. Verify refresh JWT.
2. Hash provided refresh token.
3. Find matching refresh_tokens row.
4. Confirm not revoked and not expired.
5. Revoke old refresh token.
6. Issue new access token and refresh token.
7. Store new refresh token hash.
8. Link old token to replacement.

6.7 Logout

Endpoint:
POST /api/auth/logout

Auth:
Customer/Admin

Backend logic:
1. Revoke current refresh token if provided.
2. Return success.

7. JWT MIDDLEWARE
============================================================

7.1 auth.middleware.js

Tasks:
- Read Authorization header.
- Require Bearer token.
- Verify using JWT_ACCESS_SECRET.
- Extract userId and role.
- Fetch user from database.
- Reject missing/deleted users.
- Attach req.user.

Expected req.user:
{
  id,
  role,
  phone,
  email,
  name
}

7.2 admin.middleware.js

Tasks:
- Require req.user.
- Check req.user.role === "admin".
- Reject non-admin users with 403.

7.3 customer.middleware.js

Tasks:
- Require req.user.
- Reject deleted users.
- Optional: block admin from customer-only checkout if desired.

8. SMS PROVIDER STRATEGY
============================================================

Default provider:
- AfroMessage

Provider abstraction:
- sms.service.js exposes:
  - sendOtp(phone, code)
  - sendAdminNewOrderAlert(phone, order)
  - sendTestSms(phone, message)
- sms.service.js selects provider based on SMS_PROVIDER.
- Provider files implement a common interface.

Provider files:
- afromessage.provider.js
- mock.provider.js
- future: twilio.provider.js
- future: vonage.provider.js
- future: messagebird.provider.js

AfroMessage responsibilities:
- Send OTP SMS.
- Send admin new-order alert.
- Send test SMS.
- Return normalized result:
{
  success: true,
  provider: "afromessage",
  providerMessageId: "...",
  raw: {}
}

Failure result:
{
  success: false,
  provider: "afromessage",
  error: "..."
}

SMS rules:
- OTP SMS failure returns OTP send failure.
- Admin new-order SMS failure is logged but does not fail order creation.
- Customer order status changes do not send SMS.
- Test SMS is admin-only.

============================================================
9. SUPABASE USAGE AFTER AUTH CHANGE
============================================================

Supabase PostgreSQL:
- Used through Prisma.
- DATABASE_URL is backend-only.
- Prisma migrations manage schema.

Supabase Storage:
- Used through Express only.
- Service role key is used only in backend.
- Frontend uploads product images to Express, not directly to Supabase.
- Express compresses image with Sharp before upload.
- Express uploads to product-images bucket.
- Express stores image metadata in products.images JSON.
- Express deletes old files when images are removed or replaced.

Supabase Realtime:
- Used for customer notifications.
- Express creates notification row in database.
- Frontend can subscribe to notifications table changes.
- If using Supabase client in frontend for realtime, use anon key and configure safe RLS policies.
- Alternative: avoid frontend Supabase client and use Express SSE/WebSocket later.

Supabase Auth:
- Not used.
- No Supabase Auth user ID.
- No Supabase access token.
- Express JWT is the only API auth token.
